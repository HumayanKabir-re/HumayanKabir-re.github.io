ESCI-JP

An open image extension for the Japanese locale of the Amazon's Shopping Queries Dataset (SQD or Amazon-ESCI).

More text data, weaker system

Building Mercato across English or US and Japanese locales produced a result I did not expect. The Japanese half of the benchmark is larger on every text axis that usually matters, and it still results in a weaker search engine.

Japanese carries 10,407 queries against English's 8,956 queries. 233,850 products against 164,900 products. And 297,883 graded judgments against 181,701 graded judgments. More queries, more products, more human labeling. The Japanese locale is text rich and by the numbers alone should have better performance. Yet, the English system still retrieves better, because the Japanese locale is missing the image data. Amazon-ESCI only has text data, and the SQID extension only has the US locale image data. This impacted everything from retrieval to reranking.

Two datasets are in play here. The first dataset is Amazon's Shopping Queries Dataset, SQD or Amazon-ESCI. It supplies the queries, the products and the graded relevance labels. These are the text data and it covers both locales evenly. The second dataset is Crossing Mind's SQID. It is a community extension, which adds precomputed vectors for product images using OpenAI's CLIP (Contrastive Language-Image Pre-Training) models. Specifically, it uses the clip-vit-large-patch14 (ViT-L/14) variant of CLIP, which produces 768-dimensional vectors. It covers the US locale only. No public dataset provides an equivalent for Japanese.

ESCI-JP is an attempt to fill that one gap.

What the gap costs

The missing images are not without negligible effect in Mercato. The US locale runs three retrieval channels in parallel, keyword matching, dense semantic search, and image similarity. The Japanese locale runs two retrieval channels.

During development I measured the performance (NDCG@10, NDCG@100, MRR, Recall@10, Recall@100) of the US locale before and after adding the image retrival channel. Then I fused the retrieval channels and compared the cumulative performance of adding individual channels in the pipeline. As the figure below shows the NDCG@10 metric, the image channel has a very impactful contribution to retrieval performance. It was more than the difference between the two text fusion methods, and it is the only channel that the Japanese locale does not have.

The loss propagates past retrieval. A learned reranker reorders whatever the retrievers return, and its features describe how each candidate scored in each channel. With no image channel there are no image features, so the Japanese model trains on eight where the English model has ten.

The Japanese reranker also improves its input less than the English one does, gaining 0.0121 NDCG@10 compared with 0.0319 for English. There is an important nuance about that difference. The two models differ in feature count and in the language they rank. I have not run the ablation study to isolate their individual effects. Therefore, the gap is consistent with the missing features rather being attributed solely to the missing features.

As a result, ESCI-JP is an attempt to close these gap and bring the Japanese locale up to parity with the English one. It tries to achieve this by providing a public dataset of product image vectors for Japanese.

Dataset Structure

The ESCI-JP dataset will have similar structure to SQID, with similar parquet and csv files, and a similar schema. As a result, it will have image information and visual embeddings for each products as welll as the text embeddings for the associated queries. It will be compatible with any other system that uses SQID.

Product Sampling

The dataset will be a subset of the Amazon Shopping Query Dataset (SQD or Amazon-ESCI). Speciafically, it will be using the small_version of the dataset. The split will be the train test split. The product locale will be jp. Therefore, it will have 233,850 products and 10,407 queries.

Image Embeddings

The dataset will have similar structure to SQID, with one record per product image. Each record will contain the product ID, locale, image URL, embedding vector, and model ID.

Text Embeddings

The dataset will also include text embeddings for the associated queries, following the same structure as SQID. For each query and each product in Amazon-ESCI, text embeddings will be extracted using the same CLIP model and based on the query text and product title.

Encoding, following SQID

ESCI-JP uses the image encoding approach used by SQID, so that the two datasets can be used together in any system. Therefore, it also uses the same CLIP variant clip-vit-large-patch14 that SQID uses, with the same vector dimentionality.

Matching the embedding space is important for ensuring compatibility with vectors from SQID. So this Japanese set will be encoded with the same approach.

One practical lesson carried over from working with SQID is to validate on ingest. Roughly 5% of its vectors were malformed, and they were the wrong shape rather than absent. As a vector with the wrong dimentionality can cause issues later in the pipeline, checking for it and discarding such record is a much safer approach.

Publishing Vector Embeddings

Product photographs belong to the sellers and platforms that made them. Publishing embeddings and references is a way to share the derived representations without redistributing the original images.

Following SQID's precedent, this published dataset will contain the CLIP vectors and a reference to the original image, but not the image itself. It will be licensed under an open license, and the vectors will be usable in any system that uses SQID.

This dataset would not have been possible without the Amazon Shopping Queries Dataset by Amazon.

Where it stands

In development.

It has passed the test scraphing phase and currently testing the entire pipeline on a small slice of the data. The downloadable dataset will be provided once the project is finished.
