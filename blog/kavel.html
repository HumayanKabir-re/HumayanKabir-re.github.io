Kavel

Turning a seller's photo into a complete marketplace listing

In development July 2026 4 min read Design note

A design note, not a results post. Nothing here has been measured yet. It sets out what the system should do, the parts I expect to be hard, and what would have to be true before it could be deployed.

The friction worth removing

Selling something secondhand is mostly typing. You photograph the item in about ten seconds, and then you write a title, pick a category, choose a condition, fill in brand and size and colour, and write a description. Every one of those fields is a place to give up, and marketplaces lose listings at each of them.

Most of that information is already in the photograph. A picture of a pair of running shoes contains the brand, roughly the colour, the rough condition and the category. The seller is being asked to transcribe what the image already shows.

Kavel is an attempt to close that gap: one photo in, a complete draft listing out, with the seller editing rather than authoring. The name is Dutch for a lot in an auction.

The shape of it

The obvious approach is to hand the photo to a vision-language model and ask for a listing. That produces fluent text immediately and it is the wrong design, because a model asked to describe a product will invent the parts it cannot see. It will guess a model number. It will assert a size. On a marketplace those are not stylistic errors, they are wrong facts attached to a real transaction.

So retrieval comes first and generation second.

The photo is encoded and matched against listings of visually similar items that have already sold. Those comparables are then given to the generation step as context. The model is not asked what this item is, it is asked to describe this item given these twenty similar ones. Attribute values come from what comparable listings actually used, not from the model's imagination.

This is the same architecture as Mercato, pointed in the other direction. Mercato takes a query and finds products. Kavel takes a product and finds products, then writes about the difference.

What I expect to go wrong

Hallucinated attributes are the whole risk. Retrieval grounding reduces invention but does not eliminate it. A model handed twenty comparable running shoes will happily assert a size that appeared in the comparables and is wrong for this item. The mitigation is probably to make the model emit a confidence per field and leave low-confidence fields blank rather than guessing, because an empty field costs the seller ten seconds and a wrong one costs a dispute.

Category taxonomies are deeper than they look. Real marketplaces have thousands of leaf categories with inconsistent depth. Free-text generation cannot be trusted to land on a valid leaf. That part likely needs to be a classification problem over the actual taxonomy rather than something the language model writes.

Evaluating this is harder than building it. There is no single correct listing for an item, so accuracy is not available. The measurable proxies are edit distance between the generated draft and what the seller finally published, per-field acceptance rate, and time from photo to publish. All three need instrumentation that does not exist yet, and the first version will have to be judged by reading its output.

Cold start on unusual items. Retrieval grounding works when comparables exist. For a rare or handmade item there are none, and the system degrades to exactly the unguarded generation the design was meant to avoid. Detecting that case and refusing to fill fields is more useful than degrading quietly.

What deployment would need

A listing index with images and sold prices, which is the part I do not currently have and the reason this is a design note. The public ESCI corpus has products and images but not the seller-side fields a listing needs.

Beyond the data: a vision encoder and a retrieval index, which the Mercato work already covers; a generation step that can be run on CPU or a small hosted model, since per-listing inference cost has to stay near zero; and a field-level confidence mechanism, which is the part I have thought least about and expect to matter most.

The first honest milestone is not a demo. It is a hundred items where I can compare the generated draft against what a person actually published, and count how many fields survived unedited.
